# Интеграция NEXIS backend с интерфейсом

Реализованный API v2 описан в [api-contract.md](api-contract.md). Этот документ не утверждает, что виджет уже размещён на сайте партнёра: домены/CDN и способ встраивания должны быть согласованы отдельно.

## Последовательность для UI

1. Создать приватную сессию через POST /api/session. Сохранить идентификатор в рамках браузерной сессии, передавать X-Session-Id. Для чата session_id также обязателен в JSON.
2. POST /api/agent/chat с message, language и короткой history. Отрисовать answer, sources, knowledge_sources, reasoning_steps и warnings. Шаги приходят вместе с ответом, а не через SSE.
3. Карточки брать из sources; стоимость/остаток с verified=false или null показывать как неизвестные. Вывести data_quality_warnings и время проверки. Аналоги находятся в sources[].analogs.
4. При выборе товара/количества запросить POST /api/cart/offer. Показать клиенту возвращённые ID/название, количество, цену и предупреждения.
5. Только явная кнопка подтверждения вызывает POST /api/cart/add с confirmed:true и offer_token. Не подтверждать автоматически после поиска, выбора файла или выдачи предложения.
6. После успеха отрисовать серверный answer или cart_confirmation; обновить корзину из ответа cart и показать cart_url. Статичные значения статьи, цены и остатков в UI не нужны.
7. В чате подтверждение «Да, добавь» действует для pending_offer. Повтор, вопрос, отрицание, другая сессия и несовпадающее количество не добавляют товар.
8. Загрузка: FormData с file в POST /api/agent/upload-spec; браузер сам выставляет multipart boundary. Показать matched_items, unmatched_items, quantity_warning и неполную смету. Загрузка не изменяет корзину.
9. 401 — создать новую сессию; 409 — запросить новое предложение и снова спросить подтверждение; 413/415/422 — показать ошибку файла/параметров; 429 — Retry-After; 503 — источник/OCR недоступен.

Для старых виджетов поддержан session_id в query и формат ekt_web_<UUIDv4>. Произвольные короткие идентификаторы и общая сессия default не принимаются. Для новых интеграций используйте серверную генерацию.

## Что означает ссылка на корзину

cart_url / checkout_url открывает backend /cart/<read_token>. Это текущее состояние сохранённой демо-корзины, доступ на чтение ограничен десятью минутами. Ссылка не даёт права менять позиции.

partner_cart_url ведёт на отдельную корзину ekt.kz. Позиции туда не передаются. Нет официального партнёрского POST API, переноса Bitrix cookie или скрытой имитации заказа.

Для настоящего оформления партнёр должен предоставить:

- документацию метода корзины и правил авторизации;
- способ привязки к сессии покупателя без передачи платёжных данных;
- тестовый стенд, ограничения количества/кратности/цены и идемпотентность;
- безопасный URL возврата к оформлению.

## Менеджер

POST /api/manager/escalate возвращает manual_handoff_required и официальные контакты. Комментарий никуда не отправляется; номер заявки не создаётся. Для автоматической эскалации нужен реальный CRM API.

## Развёртывание

Настройте HTTPS, BACKEND_PUBLIC_URL, точные CORS_ORIGINS и приватное хранилище NEXIS_DB_PATH. Учётные данные EKT/OpenAI доступны только backend. Не публикуйте .env, SQLite, загруженные документы или сессионные токены.

Для production требуется ограничение общего потока/частоты на reverse proxy и политика обработки пользовательских данных. Пока установленная модель может получать текст запроса и ограниченную историю, загруженные файлы остаются в локальной обработке.

Frontend ветка не изменялась в этой backend-итерации. Этот документ — инструкция для её дальнейшего подключения, а не отчёт о выполненном браузерном сценарии.
