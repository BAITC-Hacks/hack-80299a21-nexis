# Архитектура NEXIS / ChipAI

API v3, 23 сентября 2026. Один агент-консультант, серверный сервис корзины, постоянные поисковые индексы и frontend на RU/KK/EN.

~~~mermaid
flowchart TD
    UI["ChipAI: чат, карточки, корзина, файлы"] --> Proxy["nginx в Docker / прямой API в dev"]
    Proxy --> API["FastAPI: валидация, языки, CORS, лимиты"]
    API --> Agent["AgentService: маршрутизация и оркестрация"]
    Agent --> Context["Контекст выбора в RAM"]
    Agent --> Tools["ToolExecutor: пять инструментов чтения"]
    Agent --> Composer["Composer: ответ из подтверждённых данных"]
    Agent -->|"Необязательный планировщик"| LLM["OpenAI API"]
    Tools --> Catalog["EktClient: поиск, карточки, аналоги"]
    Tools --> KB["KnowledgeIndex: лексический / гибридный поиск"]
    KB --> KnowledgeDB["SQLite: знания и необязательные векторы"]
    Corpus["Материалы RU/KK/EN"] --> KnowledgeDB
    KB -->|"Необязательная векторизация вопроса"| LLM
    Catalog --> CatalogDB["SQLite: поисковый индекс товаров"]
    Import["CLI импорта с checkpoint"] --> CatalogDB
    Import --> EKT["GET API ekt.kz"]

    Cart --> Catalog
    Cart --> CartDB["SQLite: корзины, сессии, предложения"]
~~~

## Агент, инструменты и ответ

Router различает поиск, наличие, цену, характеристики, сертификат, сравнение, аналог, условия покупки и техническое объяснение. Он извлекает параметры и может выделить несколько намерений. Широкий запрос получает уточнение, а образовательный вопрос обращается к знаниям.

При наличии OPENAI_API_KEY планировщик может выбирать search_products, get_product_detail, find_analogs, query_knowledge_base и check_city_stock. Цикл ограничен тремя итерациями и шестью инструментами; аргументы проверяются сервером. Результаты всех типов инструментов собираются в Evidence. При ошибке последующего вызова модели уже полученные данные сохраняются. Без модели работают правила и те же источники.

Цена, остаток и характеристики выводятся из карточек API. Composer использует локализованные материалы знаний для пояснений; неподтверждённый модельный текст отбрасывается. Это уменьшает риск выдуманных фактов, но не доказывает полноту базы или правильность данных партнёра. История, документы и текст источников рассматриваются как данные, а не полномочия на запись корзины.

AGENT_TIMEOUT_SECONDS задаёт общий бюджет обработки (по умолчанию 10 секунд, от 1 до 30). Он передаётся сетевым и retrieval-вызовам. Это защита от бесконтрольных продолжений, а не измеренный SLA. Ответ содержит request_id, answer_language, clarification, warning_codes и diagnostics: режим, время, число инструментов, retrieval_mode и причину перехода на резервный сценарий.

reasoning_steps — статусы выполненных действий в итоговом JSON, включая коды и результат шага. Во время ожидания UI показывает обработку; потоковой передачи шагов/SSE нет. В журналы диагностики записываются идентификатор запроса и служебные показатели, а не полный текст диалога.

## Контекст диалога

DialogueContext хранит product_id, quantity, city, budget, family, language, candidate_ids, selected_ids, constraints, pending_clarification, topic и revision. Последний список позволяет выбрать «второй вариант» и сравнить кандидатов; ограничения поддерживают короткие уточнения. Новая явная позиция сбрасывает относящиеся к прежнему выбору параметры.

Контекст находится в RAM: срок 30 минут с последнего обновления, максимум 1024 сессии, до 10 ID в каждом списке кандидатов/выбора. Ключ — хеш гостевой сессии. Полные сообщения и файлы в контекст не записываются. Перезапуск очищает память диалога, хотя SQLite-корзина и индексы остаются. Контекст не заменяет действующее предложение и согласие покупателя.

## Знания и RAG

Корпус содержит 53 самостоятельных материала и 159 коротких языковых фрагментов RU/KK/EN. Материал имеет ID, версию, источник, дату/статус проверки и сведения о переводе. Фрагмент получает chunk_id и content_hash. SQLite-индекс создаётся при первом обращении или через backend/scripts/index_knowledge.py; изменения корпуса обновляют записи, удалённые документы исключаются.

Лексический поиск учитывает слова, заголовки и ключевые выражения всех переводов. Найденный материал возвращается на запрошенном языке вместе с происхождением совпадения. Он работает без OpenAI. Гибридный режим добавляет косинусное сходство embeddings и объединяет ранги; векторы хранятся в той же SQLite, отдельный векторный сервер не используется.

Построение векторов требует явного --embeddings и ключа. Поиск с ними дополнительно требует NEXIS_EMBEDDINGS_ENABLED=true; модель задаёт NEXIS_EMBEDDING_MODEL, по умолчанию text-embedding-3-small. Отсутствующие/несовместимые векторы и ошибки внешнего вызова приводят к лексическому поиску. Ответ и health раскрывают режим и состояние индекса. Реальные платные вызовы embeddings в текущем окружении не выполнялись.

Источник не означает подтверждение любого подбора производителем. Корпус отделяет просмотренные страницы от условий, требующих менеджера, и редакционных инженерных памяток. Казахские переводы требуют вычитки носителем. Пользовательские файлы автоматически в базу не добавляются. Полные правила и CLI: [database/knowledge/README.md](../database/knowledge/README.md).

## Каталог и актуальные факты

EktClient объединяет оперативную выборку EKT_CATALOG_PAGES (по умолчанию 4, максимум 50) с постоянным поисковым индексом. CLI backend/scripts/import_catalog.py постранично делает GET-запросы, ограничивает число страниц за запуск и сохраняет checkpoint. Повтор запуска продолжает импорт; --restart начинает новое поколение. HTTP 429 имеет ограниченные повторы, повторяющаяся страница останавливает импорт. Только успешная пустая страница означает завершение снимка; после неё удаляются устаревшие ID предыдущего поколения.

Индекс предназначен для нахождения товаров: из него исключаются цена, количество и склады. Перед показом выбранной карточки факты запрашиваются из API. Кеш страниц — 300 секунд, деталей — 30 секунд по умолчанию; перед подтверждённым изменением положительного количества данные обновляются принудительно.

В текущих локальном и Docker-прогонах импортированы 11 страниц / 220 товаров, следующая страница — 12, complete_catalog:false. Docker-индекс хранится на постоянном volume. Это не полный каталог и не данные, поставляемые вместе с Git/образом. Health сообщает фактические объём, checkpoint, состояние и время импорта. Даже завершённый снимок требует последующих обновлений.

## Корзина

1. /api/session создаёт случайный идентификатор гостевой корзины.
2. /api/cart/offer или /api/cart/change-offer формирует серверное предложение.
3. UI показывает товар, артикул, цену, количество, предупреждения и отдельное подтверждение.
4. /api/cart/add или /api/cart/change принимает одноразовый токен, связанный с сессией, товаром, количеством, ценой и видом операции.
5. Положительное количество требует свежей проверки каталога. BEGIN IMMEDIATE защищает проверку и запись от повторов и конкурирующего изменения.
6. Ответ возвращает актуальные позиции и ссылку с отдельным временным токеном чтения.

При добавлении quantity — приращение; при изменении — итоговое количество, ноль означает удаление. Для изменения проверяется previous_quantity. Удаление доступно при сбое каталога, но требует подтверждения. Текстовое согласие относится только к действующему chat-предложению; отрицание, цитата, вопрос и история не дают согласия. У модели нет инструмента записи.

SQLite переживает перезапуск. Цена сохранённой позиции соответствует последней подтверждённой операции; резервирования у партнёра нет. Открытие панели или ссылки не создаёт заказ и не очищает корзину.

## Frontend, языки и документы

Сервер — источник состояния корзины. localStorage хранит идентификатор гостевой сессии и язык. При 401 UI обновляет сессию, но не повторяет POST автоматически. После неопределённого результата записи UI перечитывает корзину. Неизвестная цена/остаток не превращаются в ноль; ошибки API не подменяются синтетической консультацией.

RU отправляет ru, KZ — kk, EN — en. Общая локализация покрывает ответы, сервисные ошибки, названия параметров, предложения, результаты загрузки, HTML/CSV корзины. Артикулы, бренды, числа и исходные значения каталога сохраняются. Казахский требует отдельного языкового ревью.

Файлы отправляются multipart-полем file. Backend ограничивает размер, строки/страницы/символы, проверяет сигнатуры и извлекает текст. PDF-сканы и изображения обрабатываются локальным Tesseract. Результат содержит найденные, неоднозначные и неизвестные строки, количество, проверенные цену/остаток и известную часть суммы. Неизвестное количество не заменяется единицей. Загрузка не меняет корзину и не передаёт документ модели.

## Запуск, проверка и границы

Docker Compose запускает nginx на localhost:5173 и backend на localhost:8000. В образ копируется утверждённый корпус database/knowledge; .env и рабочие SQLite исключаются из контекста сборки. Корзина, знания и каталог сохраняются в /data/nexis.sqlite3, /data/knowledge.sqlite3 и /data/catalog.sqlite3 на именованном volume. Нативный dev.py запускает Vite/FastAPI и согласует API/CORS.

RAM-контекст, оперативный кеш и лимитер локальны процессу. Несколько воркеров требуют согласованного состояния и нагрузочной проверки. Публичной deployed-ссылки в репозитории нет; нужны HTTPS, публичные адреса и настройки reverse proxy.

72 сценария backend/evals — офлайн-набор разработки на синтетическом каталоге, не независимая оценка реальной LLM. Модельный ключ отсутствовал; платные вызовы не выполнялись. Результаты новых прогонов и ограничения записываются в [журнал реализации v3](agent-v3-implementation.md).

Партнёр предоставил только GET API. Настоящая корзина ekt.kz, резерв, оплата и CRM не подключены. Остаются ограничения покрытия каталога, семейств аналогов, целочисленного количества и качества OCR.
